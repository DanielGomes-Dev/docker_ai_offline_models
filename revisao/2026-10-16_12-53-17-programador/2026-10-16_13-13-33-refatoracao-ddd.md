### DDD-6 Results mutáveis e sem igualdade ✅
**Commit:** 45e141a

**O problema:** `TtsResult` e `ImageResult` são, na prática, Value Objects: o resultado de uma síntese só importa pelo valor (bytes + mime). Mas eram classes comuns. Qualquer um podia reatribuir `result.mime = ...` depois de criado, e duas instâncias com o mesmo conteúdo não eram iguais (`==` comparava identidade). Na prática: os testes não conseguiam comparar resultados com `assertEqual(result, TtsResult(...))`, e um consumidor podia alterar um resultado compartilhado sem ninguém perceber.

**Código anterior**: `src/domain/ports/tts_provider.py:12-15` (o `image_provider.py:12-15` era igual, com `image`)
```python
class TtsResult:
    def __init__(self, audio: bytes, mime: str):
        self.audio = audio
        self.mime = mime
```

**Código depois**: `src/domain/ports/tts_provider.py:10-18` (o `image_provider.py:10-18` segue o mesmo formato)
```python
from dataclasses import dataclass


@dataclass(frozen=True)
class TtsResult:
    """Value Object: imutável e comparado pelo valor (audio + mime)."""

    audio: bytes
    mime: str
```

**Por que esta é a melhor forma:** `@dataclass(frozen=True)` é o idioma do Python para um Value Object. Ele gera `__init__`, `__eq__` e `__hash__` por valor e bloqueia a reatribuição (`FrozenInstanceError`). A assinatura de construção continua a mesma (`TtsResult(b"..", "audio/wav")` e `TtsResult(audio=..., mime=...)`), então nenhum provider precisou mudar. Alternativas descartadas: (a) escrever `__eq__`/`__hash__` à mão, que dá mais código e mais chance de erro; (b) `NamedTuple`, que também é imutável, mas vira tupla (`result[0]`, desempacotável, igual a uma tupla qualquer), o que vaza a representação; (c) Pydantic `BaseModel(frozen=True)`, que acoplaria o domain a uma lib de validação, sendo que ele hoje só usa a stdlib. Fica um custo: não há validação na criação (mime vazio passaria). Não adicionei porque nenhum caso real pede isso e o item não pedia.
**Testes:** novos `src/domain/ports/test_tts_provider.py` e `test_image_provider.py` (4 cada): igualdade por valor, diferença quando um campo muda, hash igual e imutabilidade. 95 ✅.

### DDD-5 Seleção de provider duplicada (TTS e imagem) ✅
**Commit:** 19f05fa

**O problema:** `TtsService` e `ImageService` tinham o mesmo bloco copiado: `_CONFIG_PATH`, `_load_config()`, o mapa `_PROVIDERS` e o `if` que instancia a classe pelo nome. Os `config.json` (configuração de deploy) moravam dentro da camada de application. Na prática: cada provider novo ou cada ajuste na regra de fallback precisava ser feito em dois lugares, e a application era quem sabia que existem `EdgeTtsProvider`, `GeminiTtsProvider` e `ZImageProvider`.

**Código anterior**: `src/application/services/media/tts/tts_service.py:15-40` (o `image_service.py:15-39` era cópia, com `z_image`)
```python
_CONFIG_PATH = Path(__file__).resolve().parent / "config.json"

_PROVIDERS = {
    "edge_tts": EdgeTtsProvider,
    "gemini": GeminiTtsProvider,
}


def _load_config() -> dict:
    try:
        return json.loads(_CONFIG_PATH.read_text(encoding="utf-8"))
    except (OSError, json.JSONDecodeError):
        return {"provider": "edge_tts"}


class TtsService:
    def __init__(self, provider: TtsProvider | None = None, config: dict | None = None):
        self.config = config or _load_config()
        if provider is not None:
            self.provider = provider
        else:
            name = self.config.get("provider", "edge_tts")
            provider_cls = _PROVIDERS.get(name)
            if provider_cls is None:
                raise ValueError(f"Provider de TTS desconhecido: {name!r}")
            self.provider = provider_cls(self.config.get(name, {}))
```

**Código depois**: o registry genérico em `src/infra/providers/provider_registry.py:15-35`
```python
def load_provider_config(path: Path, default_provider: str) -> dict:
    try:
        return json.loads(path.read_text(encoding="utf-8"))
    except (OSError, json.JSONDecodeError):
        return {"provider": default_provider}


def build_provider(registry: dict[str, type], config: dict, *, default_provider: str, kind: str) -> Any:
    name = config.get("provider", default_provider)
    provider_cls = registry.get(name)
    if provider_cls is None:
        raise ValueError(f"Provider de {kind} desconhecido: {name!r}")
    return provider_cls(config.get(name, {}))
```
e uma factory fina por tipo, `src/infra/providers/tts/tts_provider_factory.py:12-25` (a `image/image_provider_factory.py` tem o mesmo formato)
```python
CONFIG_PATH = Path(__file__).resolve().parent / "config.json"
DEFAULT_PROVIDER = "edge_tts"

TTS_PROVIDERS: dict[str, type[TtsProvider]] = {
    "edge_tts": EdgeTtsProvider,
    "gemini": GeminiTtsProvider,
}


def build_tts_provider(config: dict | None = None) -> TtsProvider:
    config = config or load_provider_config(CONFIG_PATH, DEFAULT_PROVIDER)
    return build_provider(TTS_PROVIDERS, config, default_provider=DEFAULT_PROVIDER, kind="TTS")
```
Neste commit, os services passaram a chamar `build_tts_provider(config)`/`build_image_provider(config)`, mantendo a assinatura antiga para o item ficar isolado. O DDD-1 removeu essa chamada em seguida.

**Por que esta é a melhor forma:** a escolha "nome no config → classe concreta" é conhecimento de infraestrutura, então a Factory mora na infra, ao lado do `config.json` que ela lê. O registry tem a lógica uma vez só, e cada tipo (TTS, imagem) declara apenas o seu mapa e o seu default. Comportamento preservado: mesmas mensagens de erro (`Provider de TTS desconhecido: 'nope'`, `Provider de imagem desconhecido: ...`), mesmo fallback quando o JSON falta ou está inválido, mesma semântica de `config or <arquivo>` (dict vazio ainda cai no arquivo). Alternativas descartadas: (a) mover o `config.json` para settings no `config.py`, que mudaria o formato de configuração do deploy e não fazia parte do item; (b) uma única factory com `if kind == "tts"`, que juntaria de novo as duas coisas que o item quer separar; (c) uma classe `ProviderRegistry` com estado, que seria mais cerimônia para algo que duas funções puras resolvem (a discussão "vale um padrão formal?" é do refatorador de design patterns). Fica um custo: `infra/providers` importa os providers concretos, ou seja, importar a factory de TTS carrega `httpx` e o módulo do Gemini. Isso não muda nada em relação a antes, porque o service já fazia esses imports. A factory de imagem importa `ZImageProvider`, que só carrega torch/diffusers na 1ª geração (lazy).
**Testes:** novos `src/infra/providers/test_provider_registry.py` (6 testes: instância com a seção, default, desconhecido, leitura do JSON, JSON ausente, JSON inválido), `tts/test_tts_provider_factory.py` (4) e `image/test_image_provider_factory.py` (3), que também conferem se o `config.json` movido é encontrado e se o default real continua `edge_tts`/`z_image`. Os testes antigos dos services continuaram passando sem alteração neste commit. 108 ✅.
