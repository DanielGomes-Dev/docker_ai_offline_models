## Divergências documentação × código

### DIV-1 Corpo que não é JSON em /tts e /image vira HTTP 500, fora do envelope
**Doc diz:** erro de payload nunca vira HTTP de erro; vira `{"status": "invalid_request", "message"}` com HTTP 200 (`docs/01-texto-para-fala-tts.md:155-157`, `src/interfaces/http/media/schemas.py:7`) · **Código faz:** `await request.json()` estoura antes do controller e o `_fail` do platform_core devolve HTTP 500 `{"detail": ...}` (`platform_core/platform_core/http/route_register.py:110`, `:88-93`) · **Teste escrito para:** comportamento atual (`test_corpo_que_nao_e_json_estoura_http_500_com_detail`).

### DIV-2 /transcribe sem o campo `upload` → 422; `payload` que não é JSON → 500
**Doc diz:** mesmo envelope `invalid_request` com HTTP 200 (`docs/02-transcricao-de-audio-stt.md:259-261`, `schemas.py:7`) · **Código faz:** `upload: UploadFile = File(...)` faz o FastAPI responder 422 antes do controller; `json.loads(form.get("payload"))` inválido vira 500 (`route_register.py:127-130`) · **Teste escrito para:** comportamento atual. Os clientes tratam ≥400 como erro, então não quebram; só o envelope não é uniforme.

### DIV-3 Default do código do ZImageProvider é `offload="model"`, que a doc diz não ser viável
**Doc diz:** com o pipeline quantizado, `cpu_offload` quebra com "meta tensor" e não é opção hoje (`docs/03-geracao-de-imagem.md:400-405`, `:471-474`) · **Código faz:** sem a chave `offload`, o default é `"model"` (`src/infra/external/z_image/z_image_provider.py:44`) e com `quantize=True` chama `enable_model_cpu_offload()` (`:89-90`). Só o `config.json` versionado (`"offload": "none"`) evita isso; se o config faltar ou for inválido, o `ImageService` cai em `{"provider": "z_image"}` (`image_service.py:26`) e usa o default problemático · **Teste escrito para:** comportamento atual (`test_code_default_without_config_is_quantized_with_cpu_offload`, `test_provider_without_config_section_offloads_to_cpu_by_default`).

### DIV-4 Comentários do Z-Image dizem que o whisper roda em CPU no mesmo processo
**Doc diz:** processos separados (`APP_ROLE`); whisper em `cuda` no container `ai-inference` (`docs/00-visao-geral.md:35-48`, `docker-compose.yml` `WHISPER_DEVICE: cuda`) · **Código faz (comentários):** "no MESMO processo… `WHISPER_DEVICE=cpu` isola o whisper" e "só cabe porque o whisper roda em CPU" (`z_image_provider.py:12-14`, `:84-86`) · **Teste escrito para:** não afeta comportamento; comentário desatualizado.

### DIV-5 `app_description` (Swagger) desatualizado
**Doc diz:** o serviço também gera imagem e é chamado por `video_automation`, `video_worker` e `llm_adapter` (`docs/00-visao-geral.md:54-70`) · **Código faz:** descrição cita só TTS e transcrição e "video_orchestrator" (`src/config.py:27-30`) · **Teste escrito para:** comportamento atual (já coberto em `src/test_config.py`).

### DIV-6 (contrato, lado do cliente) video_automation só trata `"error"`: `invalid_request` no /tts estoura KeyError
**Servidor oferece:** HTTP 200 `{"status": "invalid_request", "message": "text: Value error, não pode ser vazio"}` para texto em branco (confirmado em `test_payload_invalido_vira_invalid_request_com_http_200`) · **Cliente faz:** `_json_or_raise` só levanta para `status == "error"`; o `tts` lê `data["data_b64"]` → `KeyError`; no `transcribe`, o envelope volta como se fosse resultado (`_shared/video_automation/src/infra/clients/ai_inference_client.py:37`, `:61-63`) · **Teste escrito para:** comportamento atual do servidor. Mesma divergência que a DIV-7 do relatório do video_automation; a correção é no cliente.

### DIV-7 (contrato, lado do cliente) video_worker também ignora `invalid_request` no /transcribe
**Servidor oferece:** `invalid_request` para `payload` fora do schema · **Cliente faz:** só trata `"error"` e devolve o envelope; `_write_srt` grava SRT vazio sem erro (`_shared/video_worker/src/infra/external/whisper/transcribe_service.py:243-245`, `:224-225`) · Hoje é difícil de acontecer (o cliente sempre manda `{}` ou `{"language": str}`), mas o contrato fica frágil. O `llm_adapter` trata os dois status corretamente (`ai_inference_image_provider.py:124-128`): sem divergência ali.

Observação (não é divergência, a doc não fala nada): o upload salvo em `files/temp/audio_in/` **nunca é apagado** depois da transcrição (`media_controller.py:115-129`). Fica registrado em `test_arquivo_salvo_continua_em_disco_depois_da_transcricao`.

## Não testável sem mudar produção
Tudo foi testado por fora, mas com remendos que indicam acoplamento:

### TST-1 Serviços resolvidos por import tardio e pasta de upload fixa no cwd — `src/interfaces/http/media/media_controller.py:34`, `:37-61`, `:117`
**Por quê:** o controller cria `TtsService`/`ImageService`/`TranscribeService` por conta própria (service locator), grava em `Path("files/temp/audio_in")` relativo ao cwd e usa `time.time()` no nome. Os testes precisam trocar atributos de módulo, `chdir` e só conseguem conferir que o prefixo é numérico · **Sugestão:** injetar factories dos serviços, a pasta de upload e um relógio (DIP) → refatorador-solid.

### TST-2 MediaRoutes instancia o controller e lê o `settings` global — `src/interfaces/http/media/media_routes.py:10`, `:13`
**Por quê:** `create_app()` não aceita controller nem role; o teste E2E precisa de monkeypatch em `settings.role` e nas classes dos serviços · **Sugestão:** `create_app(settings, controller=None)` / passar o role para `MediaRoutes` → refatorador-solid.

### TST-3 Carga do pipeline importa torch/diffusers dentro do método — `src/infra/external/z_image/z_image_provider.py:63-101`
**Por quê:** só dá para testar `_load_pipe` trocando `sys.modules["torch"]`/`["diffusers"]` · **Sugestão:** extrair um "pipeline loader" injetável (o `pipeline_factory` já existe, mas pula toda a lógica de quantização/offload) → refatorador-solid.

### TST-4 Construtor do TranscribeService altera o `PATH` do processo — `src/infra/external/whisper/transcribe_service.py:27`, `:45-55`
**Por quê:** efeito colateral global (`os.add_dll_directory`, `os.environ["PATH"]`) no construtor; o teste precisa trocar `sys.prefix` · **Sugestão:** mover a injeção de DLL para o bootstrap (`create_app`/lifespan) ou um colaborador injetável.
